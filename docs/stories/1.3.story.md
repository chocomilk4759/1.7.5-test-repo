# Story 1.3: 계산기 화면

## Status

InProgress

## Story

**As a** 공업용 계산기를 쓰는 사람,

**I want** `renderScreen(expression)`이 식과 결과를 한 줄 글자로 돌려주고, 잘못된 식은 `오류:` 줄로, 빈 식은 빈 글자로 돌려주기를,

**so that** 계산 결과와 식의 문제를 한 줄에서 읽을 수 있고, 아직 식이 없을 때는 화면이 비어 있다.

## Scope and Dependencies

### 결과와 범위

이 Story의 결과는 계산기 화면 모듈 하나다. `src/screen.js`가 `renderScreen`과 `SCREEN_WIDTH`를 내보내고, `test/screen.test.js`가 AC 1~3의 동작을 확인하며, 프로젝트 루트의 `node --test`가 기존 테스트까지 모두 통과하고, `src/screen.js`가 있는 상태에서 `node ci/screen-rule.check.mjs`가 종료 상태 0으로 끝나면 확인된다.

이 Story는 PRD Epic 1 "계산과 단위"의 셋째 Story다. PRD 섹션 "목표"대로 계산기 화면은 글자를 돌려주는 순수 함수이고, 브라우저 화면은 뒤 Epic이 다룬다. 이 Story는 Story 1.1의 `evaluate`와 `CalculationError`, 기존 `formatNumber`를 쓴다. Story 1.2의 `src/units.js`는 쓰지 않는다. `docs/architecture.md#설계-원칙`이 "`src/screen.js`는 `src/engine.js`와 `src/number-format.js`만 가져다 쓴다"고 정한다.

범위 밖은 다음과 같다.

- `src/engine.js`, `src/number-format.js`, `test/engine.test.js`, `test/number-format.test.js`, `ci/screen-rule.check.mjs`, `.github/workflows/ci.yml`은 바꾸지 않는다.

- 브라우저 화면과 "결과 복사"(뒤 Epic)는 만들지 않는다.

### 기술 제약

프로젝트 구조는 `docs/architecture.md#소스-트리`와 충돌하지 않는다. `src/screen.js`와 `test/screen.test.js`는 그 표에 이미 있는 자리다. Architecture에 없는 파일은 만들지 않는다.

Architecture에서 온 제약은 다음과 같다.

- 언어와 실행 환경은 ES 모듈과 Node.js 24다. 내장 모듈만 쓰고 외부 패키지는 쓰지 않는다. 테스트는 `node:test`와 `node:assert/strict`다(`docs/architecture.md#기술-구성`).
- 공개 함수는 순수 함수로 두고 입출력이나 전역 상태를 쓰지 않는다. `src/screen.js`는 `src/engine.js`와 `src/number-format.js`만 가져다 쓴다(`docs/architecture.md#설계-원칙`).

구현할 때 놓치기 쉬운 점은 다음과 같다.

- AC 3은 AC 2의 넓은 문장을 좁힌다. `evaluate("")`와 U+0020만 있는 글자의 `evaluate`는 `CalculationError`를 던지지만 `renderScreen`은 빈 글자를 돌려준다.
- 오류는 클래스로 가린다. `CalculationError`의 `name`은 "Error"여서 `name` 글자로 가리면 모든 `CalculationError`가 그대로 나간다. 클래스를 가리지 않고 받으면 `RangeError`가 `오류:` 줄이 되어 AC 2의 "다른 오류는 그대로 던진다"에 어긋난다.
- 공백 판정이 문자열이 아닌 입력을 건드리지 않게 한다. 메서드를 바로 부르면 `evaluate`의 오류가 아닌 다른 `TypeError`가 먼저 나가고, 참거짓으로 가리면 `0`, `null`, 인자 없는 호출이 빈 글자가 되며(CC-JS-004), 글자로 바꾸어 가리면 `[]`와 `[" "]`가 빈 글자가, `["1"]`이 값 줄이 된다.
- `evaluate`에는 받은 글자를 그대로 넘긴다(N-3). 다듬은 글자를 넘기면 오류 위치가 받은 글자의 위치와 어긋나고, 지금 엔진이 거부하는 `"\t1 + 2"`가 값 줄이 된다.
- 결과가 0인 식은 빈 식이 아니다. `1 - 1`은 `1 - 1 = 0`이다. `formatNumber`에는 값만 넘기고 유효 숫자 인자를 따로 주지 않는다. `evaluate`는 유한한 값만 돌려주므로 `formatNumber`의 `RangeError`는 여기에 닿지 않는다.
- `SCREEN_WIDTH`는 내보내기만 한다. 줄의 모양에 쓰지 않는다. `{식} = {결과}`와 `오류: {메시지}`는 40글자를 넘을 수 있고 그대로 돌려준다.
- 호출 사이에 남는 모듈 수준 상태를 두지 않는다. `g` 플래그가 있는 모듈 수준 정규식은 `lastIndex`를 남긴다.

### Testing

시험 파일은 `test/screen.test.js`이고, 프레임워크는 `node:test`와 `node:assert/strict`다. 필수 점검 명령은 둘이다. 프로젝트 루트의 `node --test`는 기존 `test/engine.test.js`와 `test/number-format.test.js`까지 함께 실행하고, `node ci/screen-rule.check.mjs`는 `SCREEN_WIDTH`를 본다. 다른 넓은 실행은 필수로 두지 않는다. 테스트 대역은 쓰지 않는다. `evaluate`와 `formatNumber`는 이 프로젝트의 모듈이어서 시스템 경계가 아니다. `renderScreen`은 외부에 기대지 않는 순수 함수이므로 동작 시나리오의 수준은 unit이다. 테스트 이름과 주석은 기존 테스트 파일처럼 영어로 쓴다.

표 1의 기대 글자는 시험 파일에 글자 그대로 적는다. 시험 안에서 `formatNumber`를 불러 기대 값을 다시 계산하지 않는다. 표의 모든 행이 전달되는 시험에 닿아야 하며, Dev는 이를 SubTask 기록 문서에 적는다. 시험 파일의 U+00A0과 U+3000은 `test/engine.test.js`처럼 JavaScript 탈출 표기로 둔다. 이 Draft에서 파일 쓰기 도구가 그 표기를 실제 글자로 바꿔 저장한 일이 있었으므로, 저장한 뒤 파일의 글자를 확인한다.

##### 판정 방법

- 값 줄: `assert.equal`로 표 1의 글자와 정확히 비교한다.
- 오류 줄: 기대 글자는 `오류: `에 `{메시지}`를 붙인 글자다. `{메시지}`는 같은 입력을 시험 안에서 `evaluate`에 넣어 받은 `CalculationError`의 `message`다. 메시지의 낱말과 언어를 시험에 적지 않는다(N-4). 시험은 그 입력에서 `evaluate`가 실제로 `CalculationError`를 던지는지도 단언한다.
- 같은 오류: `renderScreen`이 던진 오류가 같은 입력의 `evaluate`가 던진 오류와 `constructor`와 `message`가 같고, `CalculationError`의 인스턴스가 아니다. 클래스 이름과 낱말을 시험에 적지 않는다(N-5, N-6).
- 표 3의 행은 행마다 받는 결과 가운데 하나와 같으면 통과이고, 던지거나 다른 글자이면 실패다. 행 사이에 같은 읽기를 쓰라고 요구하지 않는다. 제안된 공백의 범위가 여럿이어서(`docs/planning/future-work.md`의 "공백의 종류와 자리, 숫자의 범위") 탭은 공백이고 U+00A0은 아닌 구현도 받는다.

표의 `B`는 1 뒤에 0이 308개 오는 수 글자로 값이 1e308이고, `A`는 1 뒤에 0이 309개 오는 수 글자로 배정밀도에서 유한하지 않다. `D`는 `(` 100000개, `1`, `)` 100000개를 이은 글자다.
